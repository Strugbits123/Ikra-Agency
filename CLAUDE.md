## Architecture

Single-page Next.js 16 (App Router) marketing site. There is one route (`app/page.tsx`), which renders exactly two sections: `HeroNarrative` → `DefinitionSection`. Nearly all of the complexity lives in those two scroll-driven components.

**The footer you see on the page is not `components/Footer.tsx`.** That standalone component is imported by `app/page.tsx` but commented out, and is dead as long as it stays that way. The live footer is `components/definition/SiteFooter.tsx`, rendered as the second screen of `DefinitionSection`'s track — it has to live there, because the wordmark's three dots detach and land in it, so the two share measured geometry and one timeline. Edit that file for copy or layout; its dot sizing comes from `definition/dots.ts` and its fade from the tail in `definition/sequence.ts`.

### Scroll system: ScrollSmoother + GSAP pin, never CSS `sticky`

`app/layout.tsx` wraps the whole app in `components/SmoothScrollProvider.tsx`, which creates a GSAP `ScrollSmoother` over `#smooth-wrapper` / `#smooth-content`. ScrollSmoother fakes scrolling with a `transform: translate3d` on `#smooth-content` rather than native scroll, which means **`position: sticky` does not work anywhere in this app**. Any pinned/sticky-looking effect must use `ScrollTrigger.create({ pin: <el>, pinSpacing: false, scrub: 1 })` instead — see `components/hero/sequence.ts` or `components/definition/sequence.ts` for the pattern to copy, and README.md's "The one thing that will trip you up" section for the full explanation of why.

**CSS scroll-snap does not work here either**, and for exactly the same reason — the browser has no real scroll offset to snap to. `ScrollTrigger`'s own `snap` option does work (it drives `ScrollTrigger.scroll()` itself), but **nothing in this site snaps, deliberately**: a snap is a boundary cue, and the sections are supposed to read as one continuous page. The hero→definition hand-off is a cross-fade instead (see `DefinitionSection`). Full-page/one-section-per-viewport scrolling is off the table too: both scroll-driven sections need multiple viewports of scroll distance to play their sequences.

`position: fixed` **is also broken here**, and catches people out more than `sticky` does: a transformed ancestor becomes the containing block for fixed descendants, so anything `fixed` inside `#smooth-content` scrolls with the page instead of staying put. To pin something to the viewport for real, `createPortal` it to `document.body` — see `components/ScrollBar.tsx` or the custom cursor in `components/hero/HeroLayers.tsx`.

The native scrollbar is hidden unconditionally in `app/globals.css` and replaced by `components/ScrollBar.tsx`, which `SmoothScrollProvider` mounts alongside the smoother. It draws a thumb over the page with **no track**, because a native track lives in a gutter outside `#smooth-wrapper` and therefore can never show the section behind it. Two things there are easy to get wrong if you touch it: it reads the *drawn* position (`gsap.getProperty(smoother.content(), "y")`), not `window.scrollY` — those disagree for the whole `smooth: 1.2` ease — and it updates on `gsap.ticker`, not a scroll event, because the content keeps coasting after the last event fires.

`lib/gsap.ts` registers the `ScrollTrigger`/`ScrollSmoother` plugins once (guarded by `typeof window !== "undefined"`) and re-exports `gsap` alongside them — import from `@/lib/gsap`, not directly from `"gsap"`.

### The two scroll-driven components

Both follow the same five-part split, and a new scroll-driven section should too — put it in `components/<name>/` with these roles. The point of the split is that only one of the five is allowed to know about time:

| file | owns | may touch the DOM? |
|---|---|---|
| `timeline.ts` | every beat in vh, the eases, the derived `PIN_VH`/`SECTION_VH`, and the phase table | no — pure numbers |
| `sequence.ts` | the `ScrollTrigger`s, the per-frame paint, any cue clocks | yes, through refs |
| `measure.ts` (definition only) | layout figures read back from the DOM | reads only |
| geometry (`doors.ts`/`band.ts`/`seats.ts`, `dots.ts`) | solved shapes and trajectories | no — pure math |
| `*.tsx` layers | markup and classes | rendered, never animated by themselves |

The component file itself is **only refs, effects and markup** — no timing, no math. Effects stay there so each one's dependencies sit next to the state it reads, and every body is a plain function in those modules (`createHeroSequence`, `createDefinitionSequence`), not a hook, so the caller keeps ownership of the effect. Both return a `gsap.context` the effect reverts.

- `components/HeroNarrative.tsx` — a pinned section split across `components/hero/`: `timeline.ts` owns every beat and derives the section's height, `sequence.ts` the one `ScrollTrigger` that plays it, `intro.ts` the load timeline, `doors.ts`/`band.ts`/`seats.ts` the geometry, `HeroLayers.tsx`/`BandLayer.tsx`/`GapCopy.tsx`/`WavyBand.tsx` the layers, `cursor.ts` the custom cursor, `footage.ts` the background video. The component itself is only refs and effects. **Every vh figure is derived, not written down** — `PIN_VH` is a sum of the phase lengths above it in `timeline.ts`, so changing one beat moves the section's height. Don't hardcode a total anywhere (including in docs); read `SECTION_VH`. Beats are written in **vh of actual scrolling**, not 0–1 fractions: `onUpdate` converts progress via `PIN_VH` first. Note `SECTION_VH = PIN_VH + 100` — because the pin runs `top top` → `bottom bottom`, progress 0→1 covers `height − 100vh`, so multiplying progress by the *section* height overstates real scroll by ~30%. The vh framing exists so dead scroll is visible; keep the tail short — a long one reads as being stuck, and makes the release into the next section feel like a jolt. The sequence is: a small centered clip shrinks away over the closed solid-orange "doors," the doors then open in one continuous move to **stop partway**, parking permanently as orange wedges in the bottom-left and top-right corners, three lines of gap copy pass through one centre seat, then the wavy orange band and its closing line bridge the wedges, and the doors close again into a wash to the next section's gray. A separate, non-scroll GSAP timeline plays once on load (footage and headline fade in) before the scroll phases are allowed to run — gated by `introDoneRef` so the `onUpdate` that fires at `ScrollTrigger` creation doesn't snap the intro state early.
  - **A cue at the front of the section needs a scroll floor.** A "cue" here is a threshold that fires a timed tween (the opening, `drawBand`, `closeDoors`, `washGray`) rather than a window scroll scrubs through. Cues are what you want to watch — one gesture, one speed, never parked half-done — and they consume an *unknown* amount of real scroll, because the reader keeps moving while they play. Anything measured from where a cued move landed therefore inherits the scroll's speed. That is what broke the gap copy: the doors rested at 52vh / 119vh / 327vh depending on pace, so the copy was compressed 1.3×–3.3× to fit and past that cap began playing *before* the doors stopped, lines flashing past and overlapping the still-opening aperture. Scrubbing the opening fixed that and could not deliver "one scroll opens it" — a wheel notch is ~11vh and no span a door can visibly swing across fits inside one, so a length long enough to look smooth left a blank orange screen after the first scroll. The resolution is `pathP = max(cued, ramp(vh, OPEN_SPAN))` — the move may run **ahead** of the scroll and never behind it. The clock gives one-gesture completion at any gesture size; the floor bounds the landing at `DOOR_OPEN_AT`, so every mark below is a fixed number and nothing downstream inherits the reader's speed. The three tail cues need no floor because nothing is keyed behind them. `DOOR_OPEN_AT` is a *ceiling*, not a rest position — the doors land at ~17vh for a slow reader and 53 for a flick — so `LEAD_HOLD_VH` carries the slack, deliberately, because a held line of copy is something to read where the same slack at the end of the section would be a screen of flat gray. There is no test suite, so the way to check a retune is to drive the state machine yourself at a spread of scroll speeds (roughly 12 / 30 / 90 / 400 vh/s, plus discrete wheel notches) and assert the line order, the holds and the drift.
  - `intro.ts` publishes `hurry`, which `sequence.ts` calls as soon as scroll passes `SEAL_AT`. The stage is frozen until the entrance lands, so scroll accumulates underneath it — and a scrubbed opening is *read* from the position rather than played from the start, so without this the hand-off painted the doors wherever the reader had already reached (36vh at a reading pace, 144vh past it, against a 20vh opening). Any new time-driven entrance in front of a scrubbed sequence needs the same escape hatch.
  - The doors' resting position is `DOOR_REST_X`/`DOOR_REST_Y` (fractions of the viewport) against a `DOOR_PANEL_W`-wide panel. `BAND_INSET` is *derived* from those rather than restated, so the band always lands exactly on the wedges' inner edges — adjust the rest position and the band follows. It insets 2px *less* than that edge so it tucks under each wedge and no rounding difference can show a hairline of background between the orange shapes. The panels stay oversized (`-top-1/4 h-[150%]`) because the diagonal drift would otherwise expose a panel's short edge.
  - `WavyBand` is a slim ribbon: one wave definition (`waveRun`) offset up and down by half the thickness produces both parallel edges, and the copy rides an SVG `<textPath>` along the same wave — which is what tilts each character tangent to it. It marquees right-to-left forever via a linear tween on the `startOffset` attribute, shifted by exactly one repetition of the phrase so the loop is seamless; that length is measured *after* `document.fonts.ready`, since a fallback-font measurement puts a visible jump in every repeat. Not scroll-driven — it keeps running through the scroll holds.
  - **The ribbon's ends must land exactly on the wedges' inner corners** — left cap's top edge on the left wedge's top edge, right cap's bottom edge on the right wedge's bottom edge. Anything less shows a notch, because the left wedge exists only *below* its top edge and the right one only *above* its bottom edge. This is why the centre line is a straight baseline between those two anchor points **plus a sine with a whole number of half-waves** (`humps`): `sin()` is then exactly zero at both ends, so amplitude, thickness and hump count can be retuned freely without ever moving the endpoints. Keep `humps` a whole number and keep `startY`/`endY` derived from the wedge edges. A dev-only assertion in `bandGeometry` fires if either breaks.
  - The band's vertical extent is *solved*, not sampled: because the baseline tilts, the wave's extremes are not `baseline ± amplitude`, so `bandGeometry` finds the turning points from `cos(ωx) = slope/(A·ω)`. A sampled scan undershoots by a fraction of a pixel and clips the sharpest crest.
  - Amplitude is held to 15–25px for a gentle wave, with a second ceiling from the tilt budget: glyphs rotate with the path, so past roughly 40° they push out through the ribbon's edges. That ceiling only binds on a narrow phone span. If you widen the wave, shorten the span, or raise `DOOR_REST_X`, re-check it.
  - The background footage (`footage.ts`, `BACKGROUND_VIDEO_SRC`) is deliberately **not** loaded with the page: nothing behind the doors is visible until well over a second in, so it is fetched on `requestIdleCallback` and fades over the still at `/img/hero-bg.jpg`. The still covers every frame the video isn't ready for, and `paintStage` gates play/pause on the doors separately. Skipped entirely under reduced motion.
- `components/DefinitionSection.tsx` — a pinned section split across `components/definition/` on the same plan as the hero: `timeline.ts` owns every beat and the phase table, `sequence.ts` the pin plus the two edge triggers and the tail's clock, `measure.ts` the layout figures every frame is computed against, `dots.ts` the wordmark's dots and their solved ballistics, and `DefinitionLayers.tsx`/`Dictionary.tsx`/`SiteFooter.tsx` the layers. The component itself is only refs and effects. Same vh-of-real-scroll convention and the same `SECTION_VH = PIN_VH + 100` caveat as the hero, and `PIN_VH` is likewise derived from the phase lengths above it rather than stated. The statement leaves, a round window opens over a photo, the "ikra." wordmark slides left, the dictionary definition travels up the right-hand side into the composition beside it, and then the wordmark dissolves, leaving its three dots to fall into the footer. After the statement, **everything runs concurrently from 50vh** — see the phase table in `definition/timeline.ts`.
  - **Three clocks, not one, and they cannot be collapsed.** The pin drives the scrubbed phases; two smaller `ScrollTrigger`s drive the veil and the statement's entrance, and they exist separately because both must run *before* the pin does — the pin does not start until this section's top edge reaches the viewport top, and both of those fire while that edge is still crossing the screen. The tail is a third clock again (see below). A new beat here belongs to whichever of the three already owns its window.
  - The statement's exit is written on the wrapper and its entrance on the element inside it. One element cannot carry both: either `gsap.set` rebuilds the whole transform and drops the other.
  - **The photo does not scale; the window does.** The photo is a `100vw × 100vh` `object-cover` layer *inside* the round mask, counter-scaled by exactly `1/s` against the mask's own scale every frame (`placePhoto`), so it is full-bleed and pin-sharp from the first frame and the growing circle merely uncovers more of it. Scaling the mask with the photo inside it instead — the original approach — magnified a circle-sized photo ~6× past its rendered resolution. This is also why `sizes` is `100vw`: the element genuinely is.
  - `maxScale` is the farthest viewport-corner distance from the circle's measured centre, plus a 15% margin. Coverage therefore always lands at ~85% of the growth window, whatever its length — that ratio is the knob if the fade timing has to change. The fade currently starts at the growth's *midpoint*, i.e. **deliberately before coverage**, leaving 20–34% of the screen gray so the photo blooms and dissolves rather than sitting full-bleed.
  - The hero→definition seam is dissolved by **the veil**: a slab of this section's own flat `bg-gray` that this section owns and that reaches `VEIL_VH` *above* its own top edge, painting over the hero's tail (`z-40`, because the hero's layers reach `z-30` and its section establishes no stacking context). Its **opacity** is scrubbed 0→1 by a dedicated trigger; the slab itself never moves. **It is deliberately not a gradient, and a gradient cannot do this job** — a gradient is anchored to the section's top edge, so its transparent end sits at the top of the screen exactly when the boundary appears at the bottom. Opacity is independent of position, so it can be fully committed *before* the crossing begins, which is what guarantees the two sections are never visible at once. `VEIL_VH` is derived from the hero's exported `HERO_GRAY_TAIL_VH` rather than copied, so the dissolve always spans the hero's wash exactly.
  - Paint order in the stacked composition is plain tree order — circle, wordmark, definition — held together by both the circle and the wordmark being `relative`. Neither may take a `z-index`: positioned siblings paint above non-positioned ones regardless of DOM order, so making one positioned and not the other silently reverses them, and the definition has to stay above the wordmark where they overlap on a phone.
  - **The tail is the one stretch that is not scrubbed.** Crossing `TAIL_AT` fires a timed timeline — camera pan onto the footer, footer contents resolving, dots falling — that runs to completion on its own clock and rewinds if the mark is crossed back, exactly like the hero's cues. Not a preference: every earlier phase holds a *pose* when the scroll stops, but a thrown ball frozen between bounces stops reading as a ball, and a scrubbed animation freezes by definition. The camera lives inside that same timeline rather than on the scrub so the fall cannot start before the footer has stopped moving; two clocks would let scroll speed break that ordering. `TAIL_VH` is only room to keep an ordinary scroll from outrunning the ~2.8s gesture — it is not a guard and cannot be one.
  - The dots' geometry is measured, not eyeballed: `LOGO_DOTS` are fractions taken off the alpha channel of `public/img/logo-white.png`, and `FOOTER_DOT_SIZE` is *derived* from `MARK_WIDTH` so a dot is the same size at both ends and the flight is a pure translation. An independently-sized footer dot makes the dots shrink in mid-air, which reads as receding rather than falling.

Both components check `prefers-reduced-motion` on mount and skip registering any `ScrollTrigger` when it's set, rendering a static end-state instead (`DefinitionSection`'s reduced-motion path even switches its section `height` to `"auto"` since there's no pin to reserve scroll distance for). Any new scroll-driven section needs the same fallback.

### Non-obvious GSAP gotchas (see README.md for full detail)

- Tweening `scale` (or any transform property) overwrites the entire inline `transform`, silently wiping Tailwind translate-centering classes (`-translate-x-1/2 -translate-y-1/2`) the instant it runs. Center via `xPercent`/`yPercent` in the same GSAP call instead.
- Don't measure an element that starts `scale-0` with `getBoundingClientRect()` — it reports `0×0` post-transform. Use `getComputedStyle(el).width/height`.
- GSAP's ticker pauses when the tab is hidden/unfocused; animations that look "stuck" in a background tab or headless screenshot are expected, not a bug.

### Styling

Tailwind CSS v4 with CSS-first config — there is no `tailwind.config.js`. Design tokens (`--color-ink`, `--color-accent`, `--color-cream`, `--color-gray`) live in `app/globals.css` under `:root` and are re-exposed to utility classes (`bg-accent`, `text-ink/70`, ...) via `@theme inline`. Add new tokens there. The variable font (`app/fonts.ts`, Zalando Sans SemiExpanded via `next/font/local`) is wired to `--font-sans` in the same block.

### Path aliases

`@/*` resolves to the repo root (`tsconfig.json`), e.g. `@/components/Logo`, `@/lib/gsap`.
