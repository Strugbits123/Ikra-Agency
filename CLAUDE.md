## Architecture

Next.js 16 (App Router) marketing site with **two kinds of route**, and they are built to opposite plans. `app/page.tsx` is the marketing page: `HeroNarrative` → `DefinitionSection` → `CaseStudies` → `Footer`, and nearly all of the complexity in this repo lives in those three scroll-driven components. `app/work/<slug>/page.tsx` is a **case study** — a plain document with no choreography at all, assembled in `components/study/` from one typed content record (see "The case-study routes" below). When you are asked to "add a section", check which of the two you are in: a section of the marketing page needs the five-part split and a `sequence.ts`; a band of a case study needs neither and adding them would be four empty modules.

**`app/about/page.tsx` is where a section is built before it joins the marketing page**, and it is not a third kind of route — it runs `PlaygroundNarrative` → `AboutSection` → `ApproachSection` → `Footer`, each one built to the same plan as the three on `app/page.tsx`. **The route is `/about` and the section at the top of it is still `components/playground/`** — the URL was renamed and the module was not, because `components/about/` is already the founders band on that same page. So "playground" in a file or symbol name means that first section, and the page it sits on is `/about`.

**Most of the words on this site come from the client's Wix CMS rather than from this repo**, across three routes: the intro copy, the founders and the approach points on `/about` (`components/playground/content.ts`, `components/about/content.ts`, `components/approach/content.ts`), the case-study cards on the home page (`components/cases/content.ts`), and **every case study whole** at `/work/<slug>` (`components/study/cms.ts`) — all over `lib/wix.ts`. Each is fetched on the server and handed down as props, so the client can reword one, add a card, or publish a new case study without a deploy. Three things about that are load-bearing.

Each content module is **the boundary**: a CMS row is untyped and may not be there, so every field is defended in that one file and nothing downstream knows Wix exists. **What a boundary does when it comes back empty is per-section, and all three answers are different** — the founders and approach bands on `/about` return an empty array and render nothing, because a page that still scrolls with a band missing beats a route that 500s over a third party; `caseStudiesFromWix` falls back to the three cards still in `components/cases/projects.ts`, because the site's one contact panel lives inside that section (`cases/RevealPanel`) and an empty case-studies section would take it off the home page; and a **case-study route 404s**, because it has no such hostage, it heals itself within one revalidate window, and the alternative — a second copy of eight thousand words of the client's prose, kept in the repo — is a copy nobody updates. `playgroundCopyFromWix` takes the second answer and `components/playground/content.ts` says why: those two paragraphs are the entire content of a pinned section, so an empty array leaves a black viewport with a rule and a footnote floating in it, and two paragraphs are a copy somebody *can* update. Note an outage *after* a build is invisible on every route, since Next goes on serving the last good prerender.

And `export const revalidate` in a page that reads the CMS **must stay a literal**: Next reads route segment config statically, so `WIX_REVALIDATE_SECONDS` cannot be imported into that position. There are now three of them — `app/page.tsx`, `app/about/page.tsx` and `app/work/[slug]/page.tsx` — so change all four or none. (A useful check after touching any of this: `npm run build` still prints `○` against `/` and `/about` and `●` against `/work/[slug]`, all at a 1m revalidate. A single uncached fetch turns any of them into `ƒ`.)

**There are two footers on the page and they are different things.** `components/definition/SiteFooter.tsx` is rendered as the second screen of `DefinitionSection`'s track — it has to live there, because the wordmark's three dots detach and land in it, so the two share measured geometry and one timeline; its dot sizing comes from `definition/dots.ts` and its fade from the tail in `definition/sequence.ts`. `components/Footer.tsx` is a separate standalone footer, live at the very bottom of `app/page.tsx` and reused verbatim at the foot of every case study (it used to be commented out — much older guidance calling it dead is stale). Check which one you mean before editing copy: a change to `Footer.tsx` now shows on every route.

### Scroll system: ScrollSmoother + GSAP pin, never CSS `sticky`

`app/layout.tsx` wraps the whole app in `components/SmoothScrollProvider.tsx`, which creates a GSAP `ScrollSmoother` over `#smooth-wrapper` / `#smooth-content`. ScrollSmoother fakes scrolling with a `transform: translate3d` on `#smooth-content` rather than native scroll, which means **`position: sticky` does not work anywhere in this app**. Any pinned/sticky-looking effect must use `ScrollTrigger.create({ pin: <el>, pinSpacing: false, scrub: 1 })` instead — see `components/hero/sequence.ts` or `components/definition/sequence.ts` for the pattern to copy, and README.md's "The one thing that will trip you up" section for the full explanation of why.

**CSS scroll-snap does not work here either**, and for exactly the same reason — the browser has no real scroll offset to snap to. `ScrollTrigger`'s own `snap` option does work (it drives `ScrollTrigger.scroll()` itself), but **nothing in this site snaps, deliberately**: a snap is a boundary cue, and the sections are supposed to read as one continuous page. The hero→definition hand-off is a cross-fade instead (see `DefinitionSection`). Full-page/one-section-per-viewport scrolling is off the table too: every pinned section needs multiple viewports of scroll distance to play its sequence.

`position: fixed` **is also broken here**, and catches people out more than `sticky` does: a transformed ancestor becomes the containing block for fixed descendants, so anything `fixed` inside `#smooth-content` scrolls with the page instead of staying put. To pin something to the viewport for real, `createPortal` it to `document.body` — see `components/ScrollBar.tsx` or the custom cursor in `components/hero/HeroLayers.tsx`.

The native scrollbar is hidden unconditionally in `app/globals.css` and replaced by `components/ScrollBar.tsx`, which `SmoothScrollProvider` mounts alongside the smoother. It draws a thumb over the page with **no track**, because a native track lives in a gutter outside `#smooth-wrapper` and therefore can never show the section behind it. Two things there are easy to get wrong if you touch it: it reads the *drawn* position (`gsap.getProperty(smoother.content(), "y")`), not `window.scrollY` — those disagree for the whole `smooth: 1.2` ease — and it updates on `gsap.ticker`, not a scroll event, because the content keeps coasting after the last event fires.

`lib/gsap.ts` registers the `ScrollTrigger`/`ScrollSmoother` plugins once (guarded by `typeof window !== "undefined"`) and re-exports `gsap` alongside them — import from `@/lib/gsap`, not directly from `"gsap"`.

### The scroll-driven components

There are four — three on `app/page.tsx` and `ApproachSection` on `/about` — and they all follow the same five-part split, as a new one should too. Put it in `components/<name>/` with these roles; the point of the split is that only one of the five is allowed to know about time:

| file | owns | may touch the DOM? |
|---|---|---|
| `timeline.ts` | every beat in vh, the eases, the derived `PIN_VH`/`SECTION_VH`, and the phase table | no — pure numbers |
| `sequence.ts` | the `ScrollTrigger`s, the per-frame paint, any cue clocks | yes, through refs |
| `measure.ts` (all but the hero) | layout figures read back from the DOM | reads only |
| geometry (`doors.ts`/`band.ts`/`seats.ts`, `dots.ts`) | solved shapes and trajectories | no — pure math |
| `*.tsx` layers | markup and classes | rendered, never animated by themselves |

The component file itself is **only refs, effects and markup** — no timing, no math. Effects stay there so each one's dependencies sit next to the state it reads, and every body is a plain function in those modules (`createHeroSequence`, `createDefinitionSequence`), not a hook, so the caller keeps ownership of the effect. Each returns the teardown the effect calls — a reverted `gsap.context` in the first three, a killed `matchMedia` in `createApproachSequence`.

A fifth file appears where the layout itself was measured rather than designed: `metrics.ts`, holding every measured pixel figure and the `fluid()` that restates it as a `clamp()`. `study/metrics.ts` is the original and `approach/metrics.ts` follows it. It is a separate module from the layers for one reason — the only thing anyone will want to check about a figure is what it measured, and a `clamp()` written out as a Tailwind bracket string at its call site buries exactly that.

- `components/HeroNarrative.tsx` — a pinned section split across `components/hero/`: `timeline.ts` owns every beat and derives the section's height, `sequence.ts` the one `ScrollTrigger` that plays it, `intro.ts` the load timeline, `doors.ts`/`band.ts`/`seats.ts` the geometry, `HeroLayers.tsx`/`BandLayer.tsx`/`GapCopy.tsx`/`WavyBand.tsx` the layers, `cursor.ts` the custom cursor, `footage.ts` the background video. The component itself is only refs and effects. **Every vh figure is derived, not written down** — `PIN_VH` is a sum of the phase lengths above it in `timeline.ts`, so changing one beat moves the section's height. Don't hardcode a total anywhere (including in docs); read `SECTION_VH`. Beats are written in **vh of actual scrolling**, not 0–1 fractions: `onUpdate` converts progress via `PIN_VH` first. Note `SECTION_VH = PIN_VH + 100` — because the pin runs `top top` → `bottom bottom`, progress 0→1 covers `height − 100vh`, so multiplying progress by the *section* height overstates real scroll by ~30%. The vh framing exists so dead scroll is visible; keep the tail short — a long one reads as being stuck, and makes the release into the next section feel like a jolt. The sequence is: a small centered clip shrinks away over the closed solid-orange "doors," the doors then open in one continuous move to **stop partway**, parking permanently as orange wedges in the bottom-left and top-right corners, four lines of gap copy pass through one centre seat, the closing line takes that same seat on the same cadence, and the doors close again into a wash to the next section's gray.
  - **The wavy band is currently switched off, and switching it back on is a five-step uncommenting tagged `RESTORE THE WAVE`** — grep for that string; step 1, in `hero/BandLayer.tsx`, lists all five. The ribbon's *markup* is what is commented out (the `<WavyBand>` element and its import); the band's geometry, its cue machinery and its clip all still run, so the wrapper is still there and still driven, it just draws nothing. Two consequences are load-bearing and are why this is not a one-line revert. **"holding your business back" was the ribbon's marqueeing copy and is now the fourth line of `GAP_LINES`** — restoring the wave without deleting that entry says it twice. And **the closing line no longer waits for the ribbon to clear the seat**: `LEAP_AT`/`LEAP_IN_VH` are the copy family's own cadence (`LAST_LINE.out[0] + COPY_OUT_VH / 2`, `COPY_IN_VH`) rather than `BAND_CLOSE_AT`/32, and the `bandClear` gate in `sequence.ts` is commented out with them. Leaving the gate in while the ribbon is invisible is what put 51vh of bare orange between the last line of copy and "until you make the leap" — a wave-shaped wait with no wave in it. Only the *arrival* moved; the exit is still the doors' own close rescaled to reach zero at the seal. A separate, non-scroll GSAP timeline plays once on load (footage and headline fade in) before the scroll phases are allowed to run — gated by `introDoneRef` so the `onUpdate` that fires at `ScrollTrigger` creation doesn't snap the intro state early.
  - **Every cue here needs a scroll floor, not just the one at the front.** A "cue" is a threshold that fires a timed tween rather than a window scroll scrubs through. Cues are what you want to watch — one gesture, one speed, never parked half-done — but they consume an *unknown* amount of real scroll, because the reader keeps moving while they play. That costs two different things, and both have bitten this file: anything measured from where a cued move *landed* inherits the reader's speed, and a cue with less pinned scroll behind it than it needs is simply **cut off**. The doors' close was the second kind — 1.15s of move with 4vh behind it, so at any ordinary pace it was ~3% done when DefinitionSection's veil went opaque over it, and you had to scroll slower than 4.3vh/s to ever see the panels meet.
  - **`hero/flooredCue.ts` is the answer to both, and both door moves use it.** It owns the clock, the scroll bound, and the rebase-on-reversal that makes them safe to mix; `sequence.ts` just reads it. `OPEN_VH` and `CLOSE_VH` are the two spans, and they are **independent numbers on purpose — the two legs do not share a crossover speed.** The hand-over from clock to scroll happens at `span / seconds`, so the opening leads the reader up to ~49vh/s and the close only to ~22vh/s. Matching them would want a close span of ~57vh, and that is rejected deliberately: every vh of `CLOSE_VH` is scroll spent *after* a move that has already finished on its clock (stop just past `DOOR_CLOSE_AT` and the doors are shut and the stage is gray with the whole span still ahead), and it pushes the next section that much further below the fold at the moment the wash lands, which `STATEMENT_LIFT_VH` then has to clear. Short wins on both counts; being outrun is not a failure, because the floor still guarantees the panels are shut by `CLOSE_END`. A new timed beat in this section should use `flooredCue` rather than a bare `gsap.to` on a latch.
    - The bound must be **re-anchored on the rendered value at every direction flip**, and so must the clock. `read()` clamps from below going down and from above going up, and the clock is allowed to run far ahead of the scroll in both — so swapping `max` for `min` across that gap pays the whole difference in one frame. That was the doors reading fully open at 17vh and snapping to 0.18 on a small scroll back.
    - The dispatch needs a **direction term inside the span** (`scrollDir < 0 ? 0 : 1`) or the reverse is not a gesture at all. Without it the clock stays aimed at the far end for the whole way back, `min(clock, bound)` leaves the scroll bound in sole charge, and undoing a one-notch move takes five notches. The close shipped without this term; the opening has always had it. That is what broke the gap copy: the doors rested at 52vh / 119vh / 327vh depending on pace, so the copy was compressed 1.3×–3.3× to fit and past that cap began playing *before* the doors stopped, lines flashing past and overlapping the still-opening aperture. Scrubbing the opening fixed that and could not deliver "one scroll opens it" — a wheel notch is ~11vh and no span a door can visibly swing across fits inside one, so a length long enough to look smooth left a blank orange screen after the first scroll. The resolution is `pathP = max(cued, ramp(vh, OPEN_SPAN))` — the move may run **ahead** of the scroll and never behind it. The clock gives one-gesture completion at any gesture size; the floor bounds the landing at `DOOR_OPEN_AT`, so every mark below is a fixed number and nothing downstream inherits the reader's speed. The three tail cues need no floor because nothing is keyed behind them. `DOOR_OPEN_AT` is a *ceiling*, not a rest position — the doors land at ~17vh for a slow reader and 53 for a flick — so `LEAD_HOLD_VH` carries the slack, deliberately, because a held line of copy is something to read where the same slack at the end of the section would be a screen of flat gray. There is no test suite, so the way to check a retune is to drive the state machine yourself at a spread of scroll speeds (roughly 12 / 30 / 90 / 400 vh/s, plus discrete wheel notches) and assert the line order, the holds and the drift.
  - `intro.ts` publishes `hurry`, which `sequence.ts` calls as soon as scroll passes `SEAL_AT`. The stage is frozen until the entrance lands, so scroll accumulates underneath it — and the opening's scroll *floor* is read from the position rather than played from the start, so without this the hand-off painted the doors wherever the reader had already reached: 36vh at a reading pace, and 144vh past it, which is beyond `DOOR_OPEN_AT` entirely and therefore hands over with the doors already fully open and the hole, the swing and the lead line's growth all skipped. A floored cue does not save you here — the floor is exactly the part that is position-read. Any new time-driven entrance in front of a scroll-driven sequence needs the same escape hatch.
  - The doors' resting position is `DOOR_REST_X`/`DOOR_REST_Y` (fractions of the viewport) against a `DOOR_PANEL_W`-wide panel. The ribbon's inset is *derived* from those rather than restated (`inset` on the band geometry, tucking `BAND_TUCK_PX` *under* the wedge's inner edge), so the band always lands exactly on the wedges and no rounding difference can show a hairline of background between the orange shapes — adjust the rest position and the band follows. The panels stay oversized (`-top-1/4 h-[150%]`) because the diagonal drift would otherwise expose a panel's short edge.
  - **There are two door geometries, and below `md` it is the wider one** (`doorsFor(stageW)` in `hero/doors.ts`). Everything that sits in the gap is sized to the gap, and at the desktop aperture a 390px phone leaves 164px of it — too narrow for the closing line at any readable size, and narrow enough that the ribbon's amplitude was pinned by the glyph-tilt clamp. **The knob is the aperture, not `DOOR_REST_X`**, and that is not a preference: `DOOR_SEALED_AT` is the panels' overlap measured against their travel, so raising `DOOR_REST_X` alone moves it — and `CLOSE_SEALED_P`, the wash's span, the closing line's recession and `sequence.ts`'s solved `APERTURE_AT`/`SEAL_END` are all derived from it, i.e. a per-breakpoint `DOOR_SEALED_AT` means a per-breakpoint timeline. `doorsForAperture` inverts the relation instead (`restX = aperture / (2·(1 − S))`, `panelW = restX + wedge`), holding the seal fixed, so **every beat in `hero/timeline.ts` is the same number at every width** and only how much orange stays changes. Feeding it the desktop `APERTURE` returns `0.29`/`0.58` exactly — there are dev assertions on both that identity and the held seal, and they are the whole guarantee that `md` and up did not move. A third breakpoint is one more call to that solver; do not hand-write a pair.
  - `WavyBand` is a slim ribbon (**currently commented out — see `RESTORE THE WAVE` above**; everything in this bullet and the three below it describes what comes back when it is uncommented, and is kept for that reason): one wave definition (`waveRun`) offset up and down by half the thickness produces both parallel edges, and the copy rides an SVG `<textPath>` along the same wave — which is what tilts each character tangent to it. It marquees right-to-left forever via a linear tween on the `startOffset` attribute, shifted by exactly one repetition of the phrase so the loop is seamless; that length is measured *after* `document.fonts.ready`, since a fallback-font measurement puts a visible jump in every repeat. Not scroll-driven — it keeps running through the scroll holds.
  - **The ribbon's ends must land exactly on the wedges' inner corners** — left cap's top edge on the left wedge's top edge, right cap's bottom edge on the right wedge's bottom edge. Anything less shows a notch, because the left wedge exists only *below* its top edge and the right one only *above* its bottom edge. This is why the centre line is a straight baseline between those two anchor points **plus a sine with a whole number of half-waves** (`humps`): `sin()` is then exactly zero at both ends, so amplitude, thickness and hump count can be retuned freely without ever moving the endpoints. Keep `humps` a whole number and keep `startY`/`endY` derived from the wedge edges. A dev-only assertion in `bandGeometry` fires if either breaks.
  - The band's vertical extent is *solved*, not sampled: because the baseline tilts, the wave's extremes are not `baseline ± amplitude`, so `bandGeometry` finds the turning points from `cos(ωx) = slope/(A·ω)`. A sampled scan undershoots by a fraction of a pixel and clips the sharpest crest.
  - Amplitude is held to 15–25px for a gentle wave, with a second ceiling from the tilt budget: glyphs rotate with the path, so past roughly 40° they push out through the ribbon's edges. **That ceiling binding is the symptom, and the cause is always too many humps for the span** — it used to bind on every phone, forcing the amplitude to 13px, because `humps` had a floor of 3 while `width / 165` was asking for 1.6. The floor is 2 below `md` (and stays 3 above it, gated on the same `narrow` predicate that picks the aperture, *not* on a width test of its own — at 768px a floor of 2 would round to 2 rather than 3). Amplitude now lands at 18.5 with a steepest tilt of 24–31° across phone widths. If you widen the wave, shorten the span, or change the aperture, re-check it — and if the clamp is binding, reach for the hump count before the amplitude.
  - **A layer that covers a move must share its clock, not run its own.** The orange→gray wash sits at `z-25` over the panels at `z-10`, so any door travel underneath it while it is opaque is travel nobody sees. As a cue with its own 1.3s/0.8s clock it was *racing* the doors rather than accompanying them, and which won depended purely on scroll speed — coming back up it hid half the aperture opening at a reading pace and all of it at 120vh/s. It is now scrubbed off `closeP` across `CLOSE_SEALED_P → 1`, exactly the stretch where the panels overlap and there is nothing behind it to hide, so it is at zero on the frame they part at every speed and in both directions. One clock cannot drift against itself.
  - The background footage (`footage.ts`, `BACKGROUND_VIDEO_SRC`) is deliberately **not** loaded with the page: nothing behind the doors is visible until well over a second in, so it is fetched on `requestIdleCallback` and fades over the still at `/img/hero-bg.jpg`. The still covers every frame the video isn't ready for, and `paintStage` gates play/pause on the doors separately. Skipped entirely under reduced motion.
- `components/DefinitionSection.tsx` — a pinned section split across `components/definition/` on the same plan as the hero: `timeline.ts` owns every beat and the phase table, `sequence.ts` the pin plus the two edge triggers and the tail's clock, `measure.ts` the layout figures every frame is computed against, `dots.ts` the wordmark's dots and their solved ballistics, and `DefinitionLayers.tsx`/`Dictionary.tsx`/`SiteFooter.tsx` the layers. The component itself is only refs and effects. Same vh-of-real-scroll convention and the same `SECTION_VH = PIN_VH + 100` caveat as the hero, and `PIN_VH` is likewise derived from the phase lengths above it rather than stated. The statement leaves, a round window opens over a photo, the "ikra." wordmark slides left, the dictionary definition travels up the right-hand side into the composition beside it, and then the wordmark dissolves, leaving its three dots to fall into the footer. **Almost nothing here is sequential** — the window starts opening at `GROW_AT` while the statement is still sliding out, the photo's dissolve starts at the growth's own midpoint, and the definition's climb begins as the statement clears; the wordmark's slide has no window at all (it is cued off the definition's measured *position*, so it lands at a different vh on every viewport). Read the phase table in `definition/timeline.ts` for the current windows rather than assuming an order from that sentence.
  - **The statement's *presence* is the hero's, its *travel* is its own** — see `hero/handoff.ts`, the one runtime value the two sections share. Everything else that crosses the boundary is a constant one imports from the other, which is enough while both ends are *positions*. The wash to gray is not: it is cued, so it finishes wherever the reader stops, and a scroll-mapped fade could not keep station with it in either direction — the gray landed **31vh** before the words did going down (a blank gray screen with the wordmark on it), and the words outlived the doors going up. Opacity now reads `heroWash.p`, so the two are one gesture at any speed; only the `y` stays on the scrub, because it has to keep station with a moving section edge. Two consequences worth knowing: the fade eases **in** (`power2.in`), since the wash is already `sine.inOut` and a reveal curve on top would put the words up while the stage was still half orange; and the sync is keyed on `active` as well as `p`, because this section's sequence is built a commit *before* the hero's and would otherwise latch its `!active` fallback.
  - **`STATEMENT_LIFT_VH` is a constraint, not a taste.** The lift has to exceed `CLOSE_VH + HERO_GRAY_TAIL_VH +` the frame's top padding, because that is how far below the fold this section sits at the earliest offset the wash can be complete (the hero's `DOOR_CLOSE_AT` — stop on that mark and the doors shut and the stage goes gray with no further scrolling). Under it, there is nothing on screen to fade in and the gray reads as empty however the fade is timed. There is a dev assertion on it, and a second one on the other side: the lift must not exceed the span it is spread over, or the paragraph moves *down* the screen while the reader scrolls down.
  - **Three clocks, not one, and they cannot be collapsed.** The pin drives the scrubbed phases; two smaller `ScrollTrigger`s drive the veil and the statement's entrance, and they exist separately because both must run *before* the pin does — the pin does not start until this section's top edge reaches the viewport top, and both of those fire while that edge is still crossing the screen. The tail is a third clock again (see below). A new beat here belongs to whichever of the three already owns its window.
  - The statement's exit is written on the wrapper and its entrance on the element inside it. One element cannot carry both: either `gsap.set` rebuilds the whole transform and drops the other.
  - **The stage and the frame clip with `clip-path`, not `overflow-hidden`, and the top edge is deliberately open** (`OPEN_TOP_CLIP`). The statement arrives by being lifted up to `STATEMENT_LIFT_VH` above its resting place (a *fraction* of the viewport in the code, not a vh count — the assertions multiply it by 100) — it has to, because it must be on screen while this section's top edge is still below the fold — but it sits only `STATEMENT_PAD_VH` under the frame's own top edge. Under `overflow-hidden` that put it *above its own clipping container* for the whole entrance: invisible across the entire stretch where the hero washes to gray (which is what made that read as an empty gray screen), then emerging with 92% of it cut off. **Any entrance that translates an element toward a clipping edge has to be checked against that edge, not just against the viewport.** Only the top is opened; the other three edges are load-bearing — the bottom hides the definition parked a full frame below, exactly where the footer begins, and gives the camera its one-viewport window.
  - **The photo does not scale; the window does.** The photo is a `100vw × 100vh` `object-cover` layer *inside* the round mask, counter-scaled by exactly `1/s` against the mask's own scale every frame (`placePhoto`), so it is full-bleed and pin-sharp from the first frame and the growing circle merely uncovers more of it. Scaling the mask with the photo inside it instead — the original approach — magnified a circle-sized photo ~6× past its rendered resolution. This is also why `sizes` is `100vw`: the element genuinely is.
  - `maxScale` is the farthest viewport-corner distance from the circle's measured centre, plus a 15% margin. Coverage therefore always lands at ~85% of the growth window, whatever its length — that ratio is the knob if the fade timing has to change. The fade currently starts at the growth's *midpoint*, i.e. **deliberately before coverage**, leaving 20–34% of the screen gray so the photo blooms and dissolves rather than sitting full-bleed.
  - The hero→definition seam is dissolved by **the veil**: a slab of this section's own flat `bg-gray` that this section owns and that reaches `VEIL_VH` *above* its own top edge, painting over the hero's tail (`z-40`, because the hero's layers reach `z-30` and its section establishes no stacking context). Its **opacity** is scrubbed 0→1 by a dedicated trigger; the slab itself never moves. **It is deliberately not a gradient, and a gradient cannot do this job** — a gradient is anchored to the section's top edge, so its transparent end sits at the top of the screen exactly when the boundary appears at the bottom. Opacity is independent of position, so it can be fully committed *before* the crossing begins, which is what guarantees the two sections are never visible at once. `VEIL_VH` is derived from the hero's exported `HERO_GRAY_TAIL_VH` rather than copied, so the dissolve always spans the hero's wash exactly.
  - Paint order in the stacked composition is plain tree order — circle, wordmark, definition — held together by both the circle and the wordmark being `relative`. Neither may take a `z-index`: positioned siblings paint above non-positioned ones regardless of DOM order, so making one positioned and not the other silently reverses them.
  - **The travelling definition and the wordmark must not share a horizontal band, and that needs fixing in *both* space and time — either one alone leaves the words on the logo.** Getting one right and not the other is the mistake to avoid here; the section shipped with both wrong at once.
    - **In space**, the statement above them is now capped at `lg:max-w-[42rem]` and stepped out into the frame's gutter with `lg:-ml-20`, which is what holds it to four lines and to the left of the screen from `lg` up; the frame's own padding is deliberately untouched, because `measure` reads `paddingLeft` to place the wordmark's slide and moving the frame would move the logo's resting position with it. Below that, their *resting* boxes overlapped by up to 83px, because the two scale by different laws: `MARK_WIDTH` has a 240px floor that governs below ~828px while the panel's left edge is `100% − right − 42%` and keeps marching left. Two things hold it now — the panel's width is capped against `MARK_WIDTH` (a no-op from ~1102px up, so `xl` and wider are untouched), and the panel only exists from `lg`, because below that the room genuinely is not there rather than badly divided (288px of a 768px frame is padding, the wordmark floors at 240px, so the panel would get 208px) and the definition takes the in-flow rendering phones already use. There is a dev assertion on the measured clearance in `definition/measure.ts` — it checks the real boxes, not the constants, so a change to the frame's padding or to `MARK_WIDTH` trips it too.
    - **In time**, and **the slide must not have a window in vh at all** — that is the load-bearing rule, and it took two failures to find. Given a vh window anchored to its near end, the slide *finished* 35vh after the definition arrived (**at 10 of 11 viewports tested**; only 1920 escaped, and only because the clearance it needs is ~1% of the slide against 85% at 1024 — which is why this read as a 1024-only bug and was not one). Re-anchored to its far end, it fixed the landing and broke the opening instead: the slide began at ~48vh against a definition that does not start climbing until 50, so the wordmark drifted off centre with nothing on screen to explain it. Both are the same fault — a window in vh cannot know where the definition is, and that is the only thing this move is about. It is now driven off the **gap between the two**: `markP` is the definition's own approach, spread over the last `MARK_APPROACH_FRAC` of its run at the wordmark. That shape cannot start before the definition does (at `dictP` 0 the numerator is negative), lands exactly as it arrives at every viewport, and puts "how far off does it react from" in one legible fraction. The reference point is first contact with the wordmark's **box**, not level with the letterforms' *centre* — the block is on them well before that.
  - **The tail is the one stretch that is not scrubbed, and it now starts with the wordmark's dissolve.** Crossing `TAIL_AT` fires a timed timeline — dissolve, camera pan onto the footer, footer contents resolving, dots falling — that runs to completion on its own clock and rewinds if the mark is crossed back, exactly like the hero's cues. Not a preference: every earlier phase holds a *pose* when the scroll stops, but a thrown ball frozen between bounces stops reading as a ball, and a scrubbed animation freezes by definition. The dissolve was the last thing here still on the scrub and it had the same defect in a quieter form — park a fifth of the way in and the composition is letterforms at 15% under three fully solid dots; park later and it is **three orange dots alone on flat gray**. Moving it inside (`LOGO_FADE_SECONDS`, first beat) makes the whole run from first letterform to last dot one gesture, verified to leave `markOp` only ever exactly 1 or 0 at every resting probe across the pin, and it retires the `detached` two-clock patch `paintDots` needed while the dissolve and the flight were on different clocks. The camera sits *behind* the dissolve (`PAN_AT`) rather than over it, because the wordmark rides the track and the dots do not — panning early slides the letterforms out from under their own dots. `TAIL_VH` is only room to keep an ordinary scroll from outrunning the ~3.3s gesture — it is not a guard and cannot be one.
  - **The tail's cue is a measured condition, not a mark in vh, and the floor under it is paint order.** The brief was "dissolve once the definition is 30–40% above the top of the screen," and no fraction of the climb can say that: the share above the fold at climb fraction `F` is `F − (1 − F)·H/D`, and `H/D` runs 2.0–4.2 across 1024–2560 because `dictHeight` is pinned near 344px while `H` is not — so the old fixed `LOGO_FADE_FRAC` of 0.85 meant **22% on one screen and 54% on another** (46% at 1440, 25% at 1024×1366). `sequence.ts` reads `-dictY / dictHeight` per frame against `LOGO_FADE_ABOVE_FRAC` instead, which holds 0.31–0.34 everywhere. `LOGO_FADE_CAP_FRAC` is a constant backstop behind it and exists only because `PIN_VH` is the section's CSS `height` and so cannot depend on anything measured; it binds on no measured viewport. The floor is that the dots are stage children painting over the definition and are lit as the cue fires, so the cue must land *after* the block's bottom edge clears the wordmark's top — crossing at `(H + D − markTop)/(H + D)`, measured 0.63–0.74 against a cue at 0.79–0.88, worst margin 4.1vh at 1920×700. Both sides are computed from the real boxes in `definition/measure.ts` and asserted, because a docblock here once put the crossing at 0.71–0.77, which was wrong in the unsafe direction.

On one clock the close is frame-locked to the fall in both directions, and a cue cannot skip or compress frames the way a scrub does when crossed quickly — so it is *more* speed-independent than a scrub, not less.

Its height is a `--img-h` custom property rather than an aspect ratio because the originals are portrait and honouring their aspect would make the row ~490px tall; the footer has to stay inside one viewport or the overflow is trimmed off the bottom, which is where the columns and therefore the dots' targets are. **The row's height cannot move the fall**: the landing slots sit at `frameH − (columnsHeight + bottomPadding)`, independent of everything above the columns (verified 0px slot displacement at every viewport ≥768).

Covering the ~3.3s gesture wants ~150 here, and that was tried and **rejected on report** — it puts ~53vh of finished footer between the dots landing and CaseStudies arriving, in both directions, which is the grind the earlier cut from 180 → 24 existed to remove. Note the trap that made 50 look like the compromise: it restores the old *total* (281 vs 280.5) but not the felt wait, because the measured cue moved the whole tail ~30vh earlier. The reader who stops to watch is the one being optimised for. Nothing tears when the pin releases early — dots and footer are both inside the stage, so the composition leaves as one piece and `tailTween` paints through `renderTail` rather than through the ScrollTrigger, so losing the pin does not stop the clock (verified: the fall lands in the identical stage-local pose at every rate from 20 to 300vh/s). A fast reader may simply scroll past the end of it. This is the one knob for the hand-off to CaseStudies; raising it delays that hand-off vh for vh.

- `components/ApproachSection.tsx` — the client's process as a **horizontal rail with a station at each point**, on `/about` rather than the marketing page, split across `components/approach/`: `timeline.ts` the beats, `metrics.ts` every measured layout figure, `measure.ts` the figures read back from the DOM, `stepper.ts` this section's own clock, `sequence.ts` the two triggers and the one paint, `ApproachLayers.tsx` both compositions. The copy is the client's and comes from Wix — the component never sees it fetched.

The fill is **scrubbed** there, not cued — every stretch where the rail is parked has the fill parked with it. **The dots do not animate**: they measure 67 × 72 on every frame, lit or unlit, and what looks like a dot lighting up is the wipe crossing it, so a dot is not a thing that switches state but a wider part of one track. And the reference's **own three columns are not evenly spaced** (pitches of 584 and 599) — that is a Wix grid artefact, not a design, and `CELL_COUNT` gives an even third instead, which is also the only version that generalises to the N points the CMS can hand it.

The fill and the traverse share every moment they both exist in, so this is the section where two clocks over one shared moment (the hero's wash, its door close, the wordmark slide) would have cost the most. The dots' bounce is the single exception and `timeline.ts`'s `BOUNCE_AMP` sets out why it is safe: nothing is keyed to where it lands, it only has to *start* on the same frame.
  - **The gesture is one step of the rail, not the whole of it**, which is the client's own brief — one scroll runs the line to the next dot and stops there, the next takes it to the one after. So the repo-wide rule that a gesture is never left parked half-done survives, and what changes is what a gesture *is*. `measure.ts`'s `stopsFor` is where the line may rest: a dot's **coverage** point rather than its centre, since the dot has to be solid when the line stops and the bounce fires on that same frame.
  - **`approach/stepper.ts` is this section's clock and it is deliberately not `hero/flooredCue`** — which it was built on first, and the two look similar enough to be swapped back by accident. `flooredCue` bounds a move by the reader's own position, which is right when a move has one destination and cannot express this one. **Going down**, a gesture crossing two stops' worth of scroll puts the floor two stops ahead and `max` pays the difference on a single frame — the line is already there rather than drawn to it. **Coming back it is worse and unconditional**: the bound going up *is* the destination, so `min` hands the line its answer on the first frame and there is no scroll rate at which the reverse draws. Both were reported by the client, as "sometimes it jumps to the third one" and "the reverse doesn't animate", and they are one bug.
  - So the position guarantee is gone, because "every step is visible" and "the line is exactly where your scroll says" are not both available above the crossover speed. What replaces it is a **lag bound**: `n` steps behind run at `n×` the rate (`MAX_CATCH_UP`), so the catch-up takes `STEP_SECONDS` flat however far behind the line is, with every step of it drawn. At four, that covers a three-point section entirely — the line is never more than 0.4s behind the reader at any scroll rate. Past four it stops being a lag cap and becomes a floor on how short a step may get; below about six frames a step reads as a cut rather than a draw, and there is a dev assertion on exactly that.
  - **The scroll boundaries are evenly spaced and the steps are not**, which is the one place this departs from "the line is where your scroll says". The first step is 146px of lead-in and the second a whole 561px cell; charging for them in proportion makes the opening gesture a flick of the wheel and reintroduces the jump the stepping exists to remove. One gesture, one step, whatever the step is made of — and a second assertion checks a step still costs more than one wheel notch (~10.5vh), or a single gesture crosses two.
  - **`RAIL_LEAD_IN` is load-bearing rather than decorative.** The reference's line starts 82px left of its first dot, and that short run is what gives the opening scroll something to draw: without it the first dot is covered 64px into a 1685px line, so the gesture draws 0.4% of the rail and reads as the section ignoring the reader — which is why the first build gave the first dot no stop at all, and why the first scroll appeared to run straight to the second one. **It comes out of the gutter, not out of the first cell** (82 against a 110 gutter, and the relation holds at every width the row exists at), so no dot or column moves to make room for it.
  - **Drawing into the gutter is why the clip is on the content and not on the container.** The obvious arrangement — a stage window that opens for the lead-in and shuts behind it as the track traverses — cannot work: the lead-in occupies `[trackX − leadIn, trackX]` and the first cell's copy starts at `trackX`, so one `inset()` wide enough to show a pixel of the lead-in shows the copy that has slid out past it (measured at up to 41px of a heading being read in the margin). The bar is left out in the gutter on purpose and everything else clips itself at the stage's edge — `data-approach-clip="dots"` and `"copy"`, `approachContentClip` in `ApproachLayers`.
  - **The stage clips with `clip-path`, not `overflow-hidden`, and must clip horizontally without clipping vertically.** The rail is its first child at `top: 0`, so a popping dot reaches ~9px above the stage's top edge and `overflow-hidden` sliced every pop flat — the client's "the circle looks cut". `overflow-x: hidden` alone is not the answer either: one axis hidden computes the other to `auto`, and a scroll container inside ScrollSmoother's transformed subtree is its own bug. Same answer and same reasoning as `DefinitionSection`'s `OPEN_TOP_CLIP`. The dots then get `POP_OVERHANG_RATIO` of slack on their *content* clip and the copy does not, because the first dot pops across the stage's left edge at rest and the copy never crosses it under its own power.
  - **The bounce is an addition, not a transcription**, and it **fires in both directions** — as the line arrives at a dot and again as it lets go on the way back up, at the client's request. The stepped reveal is what makes that read as an answer rather than as noise: the line comes to rest on the dot either way, so the pop has something to punctuate. It always `restart()`s forwards and is never reversed — a reversed `elastic.out` starts at the full 1.28, which is a jump rather than a hit, and then unwinds its ring.
  - **Two triggers, and they are two positions feeding one index** rather than two clocks. The reveal is scrubbed off the rail's centre crossing the fold (the measured mapping, stated directly as `center bottom` → `center 10%`); the pin spans the traverse and only exists when something overflows, starting at the reveal's own end — which is the brief's "scroll horizontally after 3 are shown" stated as a position rather than a second constant. Both key off the **rail**, not the track: the track is the rail plus a screen of copy, so `center` lands ~175px lower and the whole reveal runs a fifth of its span late.
  - **Below `lg` it is a different composition, not a narrower one** — the rail stands up, the points stack beside it, and nothing is scroll-driven. Three cells across a phone would be 130px each, under the dot's own diameter, and a pinned horizontal track would mean a phone reader cannot leave the section until they have traversed every point in it. With the rail vertical there is also nothing left for the animation to say: the fill's axis and the page's are the same, so a line that fills as you scroll is always filled to exactly where you are looking. **Reduced motion gets the stack at every width** for the same reason — without the draw, the row is three columns under a solid rule.

### The case-study routes

Three static routes used to stand here (`app/work/cafe-technica`, `/qcif`, `/auto-maxx`), eleven near-identical lines apiece over three hard-coded records, and they are gone. The studies are linked from the home page, where the cards are **CMS rows of their own** (see `CaseStudies` above). **The home track's length, its pin and every cell's entrance are derived from the array that page is handed**, so a fourth study is a row in each of two collections and no code at all — verified at two cells: the traverse still matches its closed form to 0.010px and the door still opens on one notch.

**A card's link is not a field — it is its own id under `/work/`, and only when a study exists there.** A `link` column carried the path until the study pages became CMS rows keyed by the same slug, at which point it held nothing but `/work/` plus the id sitting beside it, and the only thing it could still contribute was a typo — a card that looks right in the CMS and 404s on the site, with nothing to warn anyone. `caseStudiesFromWix` reads the page collection's slugs alongside the cards and derives it, which keeps the one thing the column did earn: **a card whose study has not been written yet is an unclickable caption, not a dead link**, and it becomes a link by itself the moment that row appears. Two cached fetches on the same revalidate, so `/` is still `○`.

**An unknown slug renders the 404 page at HTTP 200, and that is Next's own behaviour rather than a fault here.** `notFound()` returns 404 for a non-streamed response and 200 for a streamed one, and this segment streams because `app/work/loading.tsx` is a Suspense boundary — the shell is flushed before the fetch resolves, so the status is already sent. What protects it is the `<meta name="robots" content="noindex">` Next injects on that path (verified present on an unknown slug and absent on a real study), so nothing soft-404s into an index. Deleting `loading.tsx` would restore the hard status and is the wrong trade: with slugs now addable without a deploy, that file covers the first visit to a study Next has never rendered.

**`generateStaticParams` is the CMS's slugs unioned with `STUDY_SLUGS`, and the union is doing real work in both directions.** It runs once per build and *not* on revalidation, so a study added in the CMS afterwards is not in the list — it works anyway, because `dynamicParams` is left at its default of `true` and Next renders an unknown slug on demand and then caches it. The floor is for the opposite case: a build that happens while Wix is unreachable still puts the live routes in the manifest, rather than leaving the home page's links pointing at nothing.

**A study can be taken off the site without being deleted, and one is: `auto-maxx`.** Both CMS collections carry Wix's own `PUBLISH` plugin (`defaultStatus: PUBLISHED`, so everything else stays live and a new row goes live by default), which gives every row a `_publishStatus` of `PUBLISHED` or `DRAFT`. A drafted row is simply not returned to the site's anonymous visitor token, so the card leaves the home track and `/work/<slug>` 404s, with **no code change and no column of our own** — and the client keeps all forty-one fields and can republish from the CMS themselves. Auto Maxx was drafted this way on 2026-09-28 rather than deleted. **Two things in the repo have to be kept in step with that by hand**, because neither can see a publish status: the slug comes out of `STUDY_SLUGS` (otherwise the build prerenders a 404) and the card comes out of `cases/projects.ts` (otherwise a Wix outage puts the study back on the home page at the one moment nobody can check it). Both are named in their own docblocks. Putting a study back is republishing the two rows plus restoring those two entries; the route itself works again on the first request either way, since `dynamicParams` is true. Its `CaseStudyDeliverables` rows are left alone — they are only ever read filtered by slug, so they are inert while the page is gone.

**The bands are a fixed sequence again, and unwinding the mechanism that replaced it was the point.** `study.bands` used to be an ordered list of `BandKey`s per record, because the studies genuinely were different pages — Cafe Technica nine bands and QCIF six, in a different order, with a brand band the others lacked — and nine `study.x && …` guards could not have expressed the reordering. The three have since been brought onto one template on purpose: QCIF's brand band is gone (its copy is that study's outcome now), its chart and quote sit where the other two put them, and **what varies is only which parts the CMS row has filled in**. So `CaseStudyPage` reads down as masthead → quote → testimonial → outcome → glance → applications → identity → deliverables → credits, and `./cms` returns `undefined` for a band with nothing in it. QCIF renders six of the nine and needs no record to say so. A half-written fourth study renders what has been written, in this order.

What stays in `CaseStudyPage` rather than coming from the CMS is presentation that is the same wherever a band appears: which side a media split's picture takes, its tone, its measured column shares. Those are the layout's, not the client's.

**The one field a study does choose is the masthead's, and three colours follow from it.** `Tone` is an enumeration rather than a free className on purpose — each entry pairs a ground with the ink that is legible on it — and it gained `navy` for QCIF, `--color-navy: #153352`, sampled off the browser chrome in a screenshot that client supplied, at seven points around the frame. `masthead.headlineClassName` is **derived** from the field and is not a column of its own: the accent is the Cafe Technica reference's, and on a *coloured* field — this site's ember or a client's navy — it is either the only orange within three bands of itself or a second orange. The three neutral fields take the accent; the two coloured ones take the band's own ink.

**The column takes a hex code as well as one of the five names, and `study/field.ts` is the whole of what that costs.** The point of the enumeration is that a name carries *decisions*, not a background — the ink, the headline's accent, and the colour of the wordmark — so a free colour has to have all three derived or the first pale field a client picks renders white type on it. It does: the ink is white or black by WCAG relative luminance (they are equal at 0.179, and it reproduces four of the five named pairings, `ember`'s deliberate white being the fifth); the headline takes the accent only where the field is near-neutral in chroma **and** the accent clears 3:1 on it, which is the pair of tests the old `tone === "navy" || tone === "ember"` was really expressing — chroma alone hands `#808080` an invisible orange headline at 1.27:1, and contrast alone keeps the accent on navy at a perfectly legible 4.20:1, which is the field the rule exists to strip it from; and the wordmark is held to a lower floor of 1.8:1 because it is a graphic rather than type, the case being prevented being a client who picks their own orange (1.24:1 on ember). Read the file's head for the figures. **Three things worth knowing.** The five names still work and are *not* resolved through any of that — the client's rows say `navy` and `dark`, and the named entries carry two decisions the arithmetic would overturn — while anything else in English is `dark`, the same fallback the column always had. `Band` therefore takes `Tone | Field`, and a `Field` paints itself inline, because Tailwind needs class strings whole at build time and a colour known at request time cannot be a class. And the lockup in `Masthead` states neither of its colours any more: `text-white` on the descriptor was safe while every masthead was black or navy and is the first thing to break when a light field arrives.

**Every picture and clip on the page is a supplied asset in a frame, and `study/Media.tsx` is the only thing that draws one.** Two things it settles are worth knowing:
  - **A clip is a list of `<source>`s, not a URL.** Wix transcodes an upload only as far up as its source resolution, so naming one in the URL is a guess about the asset — measured on this site's own clips, `720p` (which the old hard-coded URLs asked for) answers **403** on the re-cropped hero footage, where `480p` and the original both serve. `wixVideoSources` emits `480p` then the original and the browser walks the list. Now that the client can swap the clip, nothing may assume which sizes it has.
  - **The frame clips its own corners, and the radius is a floor rather than a taste.** Several of the supplied screenshots have their rounded corners *baked in*, flattened onto a flat colour rather than left transparent, so whether they show depends entirely on the band under them: `cafe.png`'s corners are `#f7f7f7`, which is `paper` exactly, and vanish — while `wow-image-2.png` and `qcif-hero-2.png` are `#d7d4d4`, which on `dark` is four grey nicks in a black field. That was reported, and the assets can no longer be the answer: the client owns them now and the next upload has whatever corners it has. So `MEDIA_RADIUS` has to **exceed the largest baked radius** or a sliver survives outside the arc — measured by walking each asset's corner diagonal and scaling to the box it is drawn in: ~12px, ~17px, ~28px (that last one being the invisible paper-on-paper case). 20px at the reference width. Verified after: zero baked-grey pixels in the Auto Maxx hero's corners, and QCIF's corner diagonal runs paper → one antialiased pixel → mockup with no grey plateau at all. **The testimonial does not go through `Media` and keeps its square corners**, and neither does the credits logo, where a clip would cut the mark.
  - **A frame is the asset's own ratio, clamped** — `frameRatio` against the `MediaFrame`s in `study/metrics.ts`. Three per-study aspect constants used to live there (`CAFE_HERO_ASPECT`, `QCIF_HERO_ASPECT`, `CRM_HERO_ASPECT`), two of them crop windows solved pixel by pixel against a letterboxed clip; a constant describing one asset is exactly what a CMS field invalidates. The range is what the *layout* can hold, not what a picture may be: the client can now put a portrait photograph in a slot the page expects a screenshot in, and an unclamped ratio there doesn't crop the picture, it reflows the band. The masthead's floor of 1.35 is the binding one — see `MASTHEAD_PAD_TOP`. Inside the range nothing is cropped at all, and every real asset lands inside its range, so this reproduces what the page drew before. **`IDENTITY_FRAME` is the one slot that holds its own shape** (its three figures are the same number): its clip is a portrait slice of a repeating grid, so the crop *is* the composition.

**Two CMS fields are marked internal and hidden from the client**, through the same field plugin as the home cards' `aspect`: the testimonial's `tint` and its `maxVh`. Both answer "how dark are this photograph's shadows" and "is this quote short enough to cap the card", which are real per-asset decisions that no wording could usefully put beside somebody's copy. **Alt text is not asked for either** and is derived per band from the study's title — the weaker half of that trade, since a hand-written alt says more, but five more fields on an already long form are five fields that get left empty. The testimonial's photograph is the exception in the other direction: its alt is empty *because* it is a tint behind a quote and carries nothing the quote doesn't.

**The testimonial card is bounded in vh, and the bound is spent on its width.** Its height is otherwise a pure function of the viewport's *width* — a share of the content box over a fixed aspect — so it takes no notice of a short window: measured on the built page it held 1027px at every height, fitting 1920x1080 with 53px to spare and overflowing 1920x900 by 127, 1920x860 by 167 and 2560x1080 by 277. `CARD_MAX_VH` (65, read off the QCIF comp's 577px card in an 890px window) is applied to the `width` through a `min()`, so the aspect is never broken to satisfy it — the same shape of answer as `IMAGE_MAX_VH` in `cases/timeline`. It is **opt-in per study**: Cafe Technica's 1045 x 824 card is measured off a capture in which the band is 1018px tall against a 910px viewport, so "fits a screen" is not a property of that page and no global value could both preserve it and fix the overflow. `testimonial.aspect` is the same story, and it is now the photograph's own ratio bounded by `CARD_FRAME` rather than a stated figure — which returns 1.271 and 1.498 against a measured `CARD_ASPECT` of 1.268 and QCIF's stated 1.498, i.e. the same two cards.

**Every testimonial multiplies now, and white type is the reason.** The measured `screen` blend (see `study/Testimonial.tsx` for the two measurements that fix it) is faithful to the Cafe Technica capture and can *only lighten*, and white copy on the ember field starts at 3.86:1 — already under the 4.5:1 that 22px type needs — so every pixel the photograph brightens takes it further down. Measured off the render, that page's card reached **1.04:1** under its own quote: white on white, and exactly the complaint. `blend: "multiply"` inverts the guarantee — the flat field becomes the *lightest* the card can ever get. The photograph is range-compressed into a pair of multipliers first, and that pair is what decides whether the card reads as the field with a photograph in it or as a dark panel laid over it: it shipped at `[0.3, 0.9]` and came out visibly darker than the band around it, and the default `CARD_TINT` band is **`[0.5, 1]`** — the lightest the photograph may leave the card is the flat ember it sits on, the darkest is half of it, which keeps the shadows from crushing the hue to black. The two numbers anyone would want to check are stated as the endpoints and the filter derived from them, never the other way round.

**The transfer is per-study, and it carries a gamma — which is why it is an SVG filter and not a CSS one.** The band maps a *nominal* [0, 1] and knows nothing about where a given photograph's tones actually fall, and the two fall in very different places: recovered from the render, **44.9% of Cafe Technica's card sits in the bottom 5% of the input range against 0.1% of QCIF's**, because one is a soft dusk street and the other a sunlit shopfront with a dark interior and a coat in it. So `[0.5, 1]` tints QCIF and puts a flat black mass across half of Cafe Technica. **Widening the band cannot answer that, and that is provable rather than a matter of taste**: to put this photograph's p25 and median where QCIF's sit, a linear map would need `hi - lo = 2.44`. Its median source grey is 0.064 — the shadows have to be *lifted*, not scaled, and that is a gamma, which the CSS shorthand filters do not have. `CARD_TINT_CRUSHED` (`gamma 0.33, [0.66, 0.91]`) is what Cafe Technica takes; `CARD_TINT` (`gamma 1, [0.5, 1]`) stays QCIF's and, at gamma 1, is exactly the linear band `contrast()`/`brightness()` gave — verified pixel for pixel against the CSS path it replaces, **worst channel difference 1, nothing off by more than that across 2.19M samples**, so one code path now serves both.

`study/Testimonial` renders it as a single `feComponentTransfer`, whose `gamma` type is `amplitude * pow(C, exponent) + offset` — i.e. `lo + (hi - lo) * s^gamma` with no arithmetic in between. Two details there are load-bearing: `color-interpolation-filters="sRGB"`, because SVG filters default to linearRGB and every figure here was measured in sRGB (which is also where `multiply` composites); and `type="saturate" values="0"`, which is what the spec defines `grayscale(1)` as, so the greyscale step is unchanged.

**What bounds how light the card can be is a highlight, not the shadows.** Specifically the brightest patch of photograph that lands under the 22px attribution, which needs 4.5:1 against white — that single patch sets the budget for the whole card, and note the gamma is not free against it either, since it lifts that highlight too. Measured on the render at 4.65:1, the card can reach 65% of the field's luminance with the photograph nearly washed out or 58% with it clearly readable; the gamma is still worth having, because at 65% a linear map measures 4.32:1 and fails where `gamma 0.4` measures 4.65:1 and passes. Cafe Technica ships at **60% of the field** with the figures in the photograph still legible. An earlier pass at a linear `[0.6, 0.93]` matched QCIF's tonality exactly — median multiplier 0.619 to 0.619, 43% of the field to 44% — and was still reported as too dark, which is the lesson: **the eye reads the dark mass, not the mean.**

**The two blocks of copy are verified against their own thresholds rather than the card against one**: the quote is 37px, which WCAG counts as large text at 3:1, and the 22px attribution needs 4.5:1. One number for the card fails it on a bright sky no type ever crosses, and letting the ceiling reach the field exactly means the brightest pixel is 3.86:1 regardless. Measured off the render with the type hidden (so glyph antialiasing cannot be read as background): QCIF lands 4.09-4.29:1 under the quote and 5.14-5.37:1 under the attribution, and Cafe Technica **4.56-4.59:1 and 4.71-6.16:1** across 390/768/1024/1280/1440/1902/2560, sitting at 60-61% of the field at every one of them.

**Every band overlaps the one below it by 1px, and that is not cosmetic.** ScrollSmoother translates `#smooth-content` by a fractional number of pixels, so two `<section>`s that share an edge in layout round it independently when they rasterise and the cream body bleeds through the gap — but only *while the page is moving*, which is why it never shows in a screenshot. On QCIF's navy, where two bands of the same colour meet, it reads as a grey rule under the masthead. Measured across a real wheel scroll by looking for a row that is off-navy at five x positions spanning the viewport (full width is what separates a seam from an antialiased glyph — getting that wrong sends you chasing the copy): without the overlap the seam deviates from navy by up to **57 counts** on essentially every frame; with it, by 1, on none. `BAND_BLEED` in `study/primitives.tsx`. Same problem and same answer as `IMAGE_SEAM_BLEED_PX`.

**Nothing in `components/study/` itself animates, and that is a finding rather than an omission.** The reference recording is a plain scroll-through: no band pins, nothing fades in on approach, and no element moves relative to another as the page passes. So `components/study/` has no `sequence.ts`, no `matchMedia` and no reduced-motion branch of its own — the only transitions in that directory are two link hovers, which the global rule in `app/globals.css` already flattens. Don't "bring it in line" with the three marketing sections; the five-part split would be four empty modules here.

**The one band that does move is `glance`** (all three studies carry it now) — a bar chart rendered by `components/growth/GrowthBars.tsx`, a sibling directory to `study/`, not a file in it. Its own reference recording *is* scrubbed, but the bars are deliberately played on a clock instead of a scrub: `growth/timeline.ts` owns every beat, `growth/sequence.ts` builds one paused GSAP timeline per row and `play()`/`reverse()`s it off a `ScrollTrigger`, `growth/metrics.ts` the measured layout — the same split the three marketing sections use, minus a geometry file. It does check `prefers-reduced-motion` and bails out of registering any trigger; that works as a plain early return because the markup already ships as the finished chart (`--grow: 1`) and the sequence's first act is animating it down to zero, so "reduced" and "not yet mounted" are the same DOM state. `GrowthBars` renders no `Band`/`Measure`/`Display` of its own — `CaseStudyPage`'s `glance` case supplies those — which is what keeps it usable on a route that has none of those primitives.

- **Every figure in `metrics.ts` was measured off a reference recording, not chosen** — the same standard `cases/timeline.ts` holds. The capture is 1902 × 910 and **tears badly while scrolling**, so only frames the recorder held still are usable (t=0.30 / 4.40 / 9.30 / 13.00); a torn frame stitches two scroll positions together and will happily show you the same paragraph twice at two heights. Type sizes were solved rather than eyeballed: measure a line's ink width, divide by the exact advance-width sum of its string taken from the TTF, and eight independent lines across all four bands agree at 21.7 → **22px**. The serif fits at **37px**, from a 26px cap height and confirmed by its 54.5px line pitch.
  - **The body text is one size everywhere and two leadings.** 22px throughout, at a 35px pitch (1.59) in the masthead and the outcome and a 28px pitch (1.27) in the pull quote's two columns — measured across ten consecutive lines in each, to the pixel. Unifying them is the obvious tidy-up and it is wrong: the tight block is what lets those two columns sit under a three-line display line without the band growing a screen taller.
  - **`fluid(min, ref, max)` is the only way a size gets into the page.** It restates a measured pixel figure as `clamp(floor, <its share of 1902>, ceiling)`, so at the reference width every value is exactly what was measured, and away from it the page scales instead of breaking. That is also why sizes arrive as inline styles rather than Tailwind classes — writing the same `clamp()` out as a bracket string at each call site would bury the measured number, which is the only thing anyone will want to check.
  - **Three different gutters, all measured.** Copy sits at 96px; the masthead's three columns at 104px, because its 585px column pitch only closes against 104 (104 + 585 + 585 = 1274, measured 1274); and the wordmark's ink starts at 70, outside both. `logo-white.png` is cropped to its alpha with no bleed at all, so that last one is the reference's own choice and not an artefact of the asset.
  - **Two blocks deliberately do not reach the right gutter**, and squaring them up is the change to avoid. The pull quote's columns are 48.4% / 34% with a 3.3% gap, leaving 14.3% standing; the testimonial's photo panel is 61.1% wide starting 8.25% in, so its centre lands 191px left of the page's. Both read as *placed* rather than justified because of the space they leave. A 12-column grid reproduces the pull quote's left column and its offset exactly and cannot hit the right column at any span, which is why the shares are stated rather than derived.
  - **The pull quote's display line has a measure of its own** (`QUOTE_MEASURE`, 70%). Left to the full content box it sets as two lines instead of the reference's three and the band loses a whole line of height. The quotation marks are outdented 54px into the gutter and 34px above the line box, which puts them *behind the first word* — that overlap is the effect, and clearing it leaves them floating in the gutter alone.
- **The testimonial's duotone is a screen blend over a greyscale photo, and it was solved rather than guessed.** Two measurements fix it. The panel's darkest pixel has luminance 95.1 against the field's own 95.7, so the photograph only ever *lightens* the field — which rules out multiply, overlay and any semi-transparent scrim. And screen over a grey `v` predicts channel relations independent of `v` — (1−R)/(1−G) = 0.211 and (1−B)/(1−G) = 1.090 against this field — which 3,727 sampled reference pixels return as 0.210 and 1.102. The first pass used `mix-blend-luminosity`, the intuitive reading of a duotone: it reproduces the hue but not the tonal floor, so the panel came out at mean luminance 50 against the reference's 107 and every shadow crushed to black.
  - The panel is a **one-cell grid holding a ratio-only spacer and the copy in the same cell**, not a `relative` box with an `aspect-ratio` on it. `aspect-ratio` is a *preferred* size and not a floor: content taller than it simply overflows, and under `overflow-hidden` that cuts the last line off silently. The grid makes the height `max(ratio, copy)`.
  - The copy block is `relative`, and that is load-bearing rather than tidy. The photo is `<Image fill>`, i.e. positioned, and **a positioned element paints above a non-positioned sibling whatever the tree order says** — left static, the whole quote renders under the photograph as a faint ghost. Same rule as the stacked composition in `DefinitionSection`.
- **The masthead's top comes from a separate screenshot, because the recording starts below it.** The site mockup at the top right is clipped by the capture's very first frame, which is how you can tell there is more above. Two things about that hero are easy to get wrong and were, in the first build:
  - **The space to the left of the mockup is a line of copy, not a picture** — two lines of serif in the brand accent, vertically centred against the mockup. There is no photograph anywhere in this band.
  - **The band's opening is a constraint rather than a rhythm: the intro row below the hero has to be on screen before the reader scrolls.** Five figures stack up to it — 18 (`MASTHEAD_PAD_TOP`) + 75 (the lockup) + 92 (`MASTHEAD_MARK_GAP`) + 438 (the hero row) + 195 (`MASTHEAD_MEDIA_GAP`) — landing "MAY 2026" at 831 against a measured 826, inside a 907px viewport. Raise any of the five and it goes under the fold; a 56px pad, which is what shipped first, put it at 878 and cut it off.
  - The hero row sits on the page's own 96px gutter, **not** the 104px one the intro columns below it use — measured, the headline starts 8px left of "MAY 2026", which is why the band holds three `Measure`s rather than one.
- **`logo-white.png` already draws its own trademark**, raised over the final period. That is why its overall aspect is 2.441 while the reference's wordmark alone measures 2.167 — the two only disagreed because they were measuring different things, and setting a `™` beside it in markup renders the mark with two. `MARK_WIDTH` is the *total* width including that TM, and it is derived: the wordmark is the first 86.8% of the file's ink and 98.7% of its height, so at 120 the "ikra." draws at 104 × 48.4 against a measured 104 × 48. The descriptor under it is **17px on a line-height of exactly 1** — it looks far too large written down and is right on screen; solving both of its words against their advance widths returns 16.98 and 16.82, and the measured line pitch is 17.
- **`BrowserMock` and `SitePreview` are gone, and the reasoning they carried is worth keeping.** They drew a browser frame in `cqw` (a size container, so the chrome scaled as one piece at both the widths it appeared at — a `scale()` on a fixed frame blurs hairlines at every non-integer factor) with the delivered site inside it as *markup rather than a screenshot*, because no capture of that client's homepage existed and a stock photograph in a browser frame reads as a stock photograph in a browser frame. Every study now supplies its own asset out of the CMS, so "the client has no screenshot" stopped being a state this page can be in, and drawing a mockup over a client who did supply one invents an interface. `OUTCOME_MOCK_WIDTH` (39.9%, the mockup's inset from the right gutter) went with them; a supplied capture takes the half-column whole, which is what its comp shows. Bring them back and you want the container-query sizing with them.
- The serif is **Times New Roman, as a system stack rather than a webfont** (`--font-serif` in `app/globals.css`). It ships with Windows and macOS, so it costs no request and no preload; Linux and Android fall back to the generic serif — Liberation Serif or Noto Serif in practice, metrically close enough that the measured sizes in `study/metrics.ts` still set the same lines. Every call site reads the token, so a licensed face is one declaration. **Do not self-host Times New Roman** — it is Monotype-licensed; if it has to be exact on every platform, Tinos on Google Fonts is free and metric-compatible. A Playfair Display stand-in stood here first, matched to the capture by eye, and it is gone: once the token stopped pointing at it nothing read `--font-playfair`, but `next/font` went on preloading its woff2 on all four routes, the home page included, where no serif ever renders.

**A route change is covered, because the gap between the two pages is cream.** `body` is `--color-cream` and both studies open on a dark field, so any frame where the old page has gone and the new one has not painted is a white flash between two dark screens. Two windows, two answers: `app/work/loading.tsx` is the route-level fallback for the router still fetching the segment (mostly a development concern — the studies are prerendered and prefetched), and `components/RouteCover.tsx` covers the swap itself. `CaseLink` raises it **on click**, which is the earliest signal there is; `SmoothScrollProvider` takes it down after the scroll reset and the trigger refresh, on the second rAF. It is a sibling of `#smooth-wrapper` rather than a portal — already outside the transformed subtree, so `fixed` holds without waiting for `document` — and it is always mounted with only its opacity moving, so it goes up on the same frame as the click. **The fade is one-way**: easing it in showed the flash through it for as long as the flash lasted (measured 346ms of partial cover), so it appears instantly and only leaves over `FADE_MS`. Verified: zero uncovered frames between the click and the swap.

**Navigating between the two kinds of route needs `SmoothScrollProvider`'s help, and it will not happen by itself.** The provider lives in the root layout, so the smoother is created once and survives navigation while the page under it is swapped. Two things then go wrong unless the provider fixes them on a `usePathname()` change. **The scroll position does not reset** — ScrollSmoother fakes scrolling with a transform and `normalizeScroll` takes the wheel, so Next's own scroll-to-top has nothing real to act on, and opening a case study from halfway down the home page lands you halfway down the case study. **And every `ScrollTrigger`'s start and end are stale**, having been measured against the previous document's height. `smoother.scrollTo(0, false)` and `ScrollTrigger.refresh()` handle both. The effect is guarded on the path having actually changed, because it also runs on mount, and a `scrollTo(0)` there would fight the browser restoring the reader's position after a reload.

**Back and forward have to be handled separately, and a comment here used to claim they didn't** — that the router's own scroll restoration landed after the reset and won. It does not: measured, parked at 6000 on the home page, into a case study, Back, and both `window.scrollY` and the transform read 0, because `normalizeScroll` means the position Next would restore is not the position the page is drawn at and the reset is the last word either way. Clicking a card and pressing Back dropped the reader at the top of a very long page. So the provider keeps its own `scrollMemory` — a passive `scroll` listener writing `smoother.scrollTop()` under the current path, recorded continuously because by the time the route effect runs the old position is already gone — flags history navigations off `popstate`, and restores instead of resetting. Three things about it are load-bearing. The refresh must come **before** the restoring scroll, or a jump past the old document's height is clamped. `popstate` and the cover it raises are both guarded on the pathname actually changing, because a traversal that doesn't change the route never runs the route effect, and a cover raised with nothing to lower it is a black screen over a working page. And the restore **releases the hero's initial scroll lock** (`unlockInitialScroll`): going back to `/` remounts `HeroNarrative`, whose mount effect locks — and a child's effects run before its parent's, so the smoother is already `paused(true)` by then. A paused smoother doesn't just ignore the scroll, it drags the window back to its own position ~100ms later, which is what made the first attempt at this look like it had changed nothing. Unlocking is also right on its own terms: the lock exists so the hero's entrance can play unscrolled, and a reader returning 6000px down the page is neither watching it nor able to scroll for the second and a half it would hold them. Verified at 1440 with the smoother and at 700 without it: parked 6000 → study 0 → back 6000 → forward 0.

**And there is a second lock behind that one, on the far side of the page: the restore lands *past* DefinitionSection, which used to start that section's tail gesture from zero and freeze the reader for the rest of it.** The reported symptom was "I come back and can't scroll down", and it is not the hero's lock — the reader who hits it is well below the hero. Restoring into `CaseStudies` puts the definition's pin at progress 1 in a single frame, so its `render` both fires `runTail(true)` — a ~3.3s gesture, from the start — and finds the pin's `TAIL_VH` allowance already spent, which is exactly the condition `lockTailScroll` exists for. Measured at 1920×1080: `scroll-locked` on and the drawn position immobile for **2.5s** with the wheel turning the whole time, then normal. The fix is in `definition/sequence`, not here, and it turns on distinguishing a *jump* from a scroll: `TELEPORT_VH` (100, half that pin) against the pin's own per-frame travel, which the smoother bounds to ~13px at a reading pace and ~14vh at the hardest flick it will pass through. Past that threshold the tail is **placed** at its end state rather than played — nobody is watching a fall that is already off the top of the screen, and there is no scroll left to cover it. A reload deep in the page and a drag of `ScrollBar` are the same shape and get the same answer; `lastVh` starts at 0 so a sequence *built* while the reader is already down there reads its own first frame as the jump it is. The outrun-reader case is untouched, because that reader crosses `TAIL_AT` and the pin's end on separate frames — verified after: at a reading pace the wordmark still dissolves through 0.82 → 0.43 → 0.05 rather than snapping, a hard flick still gets its hold (3.15s, then released), and the restore now locks on **zero** frames and moves on the first one.

Every scroll-driven component checks `prefers-reduced-motion` on mount and skips registering any `ScrollTrigger` when it's set, rendering a static end-state instead (`DefinitionSection`'s reduced-motion path even switches its section `height` to `"auto"` since there's no pin to reserve scroll distance for, and `ApproachSection` renders its stacked composition at every width). Any new scroll-driven section needs the same fallback. Gate it on a `mounted` flag as well as the motion mode: `matchMedia` cannot be read until an effect has run, so the first commit reports "no preference" whatever the reader's setting is — and where the sequence pins, a pin built and reverted a commit later is a visible jump.

### Non-obvious GSAP gotchas (see README.md for full detail)

- Tweening `scale` (or any transform property) overwrites the entire inline `transform`, silently wiping Tailwind translate-centering classes (`-translate-x-1/2 -translate-y-1/2`) the instant it runs. Center via `xPercent`/`yPercent` in the same GSAP call instead.
- Don't measure an element that starts `scale-0` with `getBoundingClientRect()` — it reports `0×0` post-transform. Use `getComputedStyle(el).width/height`.
- GSAP's ticker pauses when the tab is hidden/unfocused; animations that look "stuck" in a background tab or headless screenshot are expected, not a bug.

### Styling

Tailwind CSS v4 with CSS-first config — there is no `tailwind.config.js`. Design tokens (`--color-ink`, `--color-accent`, `--color-cream`, `--color-gray`) live in `app/globals.css` under `:root` and are re-exposed to utility classes (`bg-accent`, `text-ink/70`, ...) via `@theme inline`. Add new tokens there. The variable font (`app/fonts.ts`, Zalando Sans SemiExpanded via `next/font/local`) is wired to `--font-sans` in the same block.

### Path aliases

`@/*` resolves to the repo root (`tsconfig.json`), e.g. `@/components/Logo`, `@/lib/gsap`.
